# AGENTS.md — `hivemind-email`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

A HiveMind transport carried over ordinary SMTP/IMAP mailboxes instead of
HTTP/WebSocket. It ships two separate surfaces sharing one carrier
(`EmailCarrier`/`SMTPIMAPTransport` in `carrier.py`): `EmailWormhole`, a
`NetworkProtocol` that relays encrypted HiveMind wire-protocol frames between
two PGP-keyed peers, and `EmailBridge`, an open natural-language gateway that
turns any inbound email into an utterance and mails back the hive's spoken
reply. `HiveMindEmailClient` is the satellite-side client mirroring
`HiveMindHTTPClient`'s connect/emit/run/close API over the email carrier. Part
of the [HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol
for connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
[hivemind-usenet](https://github.com/JarbasHiveMind/hivemind-usenet) is the
sibling repo this one mirrors structurally, swapping NNTP for SMTP/IMAP —
check it for prior art before inventing a new pattern here.

## Layout / build / test

- Package module: `hivemind_email/`. Tests live in `tests/` (check before
  adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks the
  carrier/transport and `HiveMessageBusClient`, so it runs without a live
  mailbox or hub — that also means it cannot catch a real handshake hang or a
  real IMAP/SMTP break; treat it as a shape/wiring check, not a live-behaviour
  guarantee.
- Python is capped `>=3.10,<3.13`: the carrier's PGP crypto (`remailers` ->
  PGPy) imports the stdlib `imghdr` module, removed in 3.13. Do not "fix" this
  by dropping the cap without first removing the `imghdr` dependency.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **`EmailBridge._get_hm_client()` builds and connects `HiveMessageBusClient`
  lazily, on first use, not in `__init__`.** That part follows the composition
  pattern correctly — the client is not connected at construction time.
  `connect()` is called exactly once per client instance (`self._hm_client` is
  cached); never add a second `connect()`/`run_forever()` call anywhere in the
  bridge or client.
- **`connect()` currently does not bound `handshake_max_retries` — this is a
  standing defect, not a documented trade-off.** The `hivemind_bus_client`
  floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever. As written,
  `EmailBridge._get_hm_client()` will hang indefinitely against a stalled or
  unreachable hub (down, wrong key) instead of failing fast, and every queued
  session worker blocks behind it. Any change touching `_get_hm_client()`
  must add an explicit finite `handshake_max_retries`, ideally exposed as a
  constructor parameter so operators can tune it — do not treat the current
  unbounded call as acceptable prior art to copy.
- **The hub owns ACL, not this bridge or wormhole.** A freshly registered
  HiveMind client is denied every message type until an admin runs
  `hivemind-core allow-msg recognizer_loop:utterance <client_id>` (and
  usually `speak`). Neither `EmailBridge` nor `HiveMindEmailClient` can grant
  themselves permissions; a message silently dropped on the hub side is the
  hub doing its job, not a bug here. `allowed_senders` on `EmailBridge` is a
  separate, bridge-side filter over which email addresses may originate
  traffic — it is not a substitute for hub-side message-type ACLs.
- **Rejected credentials must fail fast**, once `handshake_max_retries` is
  bounded (see above): a wrong `hive_key`/access key should turn into a clean
  failure, not a bridge that spins forever looking connected. Do not add
  retry/backoff logic on top of `connect()` that defeats a bound once one
  exists.
- **Forward upstream responses verbatim.** `EmailBridge._process_item()` mails
  back `client.ask(...)`'s return value unmodified except for wrapping it as a
  reply (`Re: <subject>`); do not reformat, truncate, or add bridge-specific
  decoration to hub-authored text. The one exception is the fixed fallback
  string used when the hive query itself raises — that is bridge-authored by
  design because the hub sent nothing to relay.
- **Do not confuse the wormhole and the bridge.** `EmailWormhole` is a
  peer-to-peer, PGP-keyed protocol transport that carries raw `HiveMessage`
  frames and never interprets their contents as natural language.
  `EmailBridge` is the open NL gateway and, by default, has **no allowlist**
  — anyone who emails it gets an answer. A change that blurs this boundary
  (e.g. routing wormhole traffic through the bridge's NL path, or giving the
  bridge PGP/hSub framing) is almost certainly a design mistake.
- **Per-session FIFO.** `EmailBridge` serialises replies per sender through a
  `_SessionQueue` keyed by a stable, non-`"default"` `session_id`
  (`_session_id()`). Any new inbound-email code path must go through
  `_get_session_queue()` rather than calling the hive directly, or replies to
  the same peer can arrive out of order.
